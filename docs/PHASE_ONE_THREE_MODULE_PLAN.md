已完成一批可运行的 P0 修复和知识维护基础功能，代码与原有未提交修改增量合并。本批包含 28 个源码、测试及配置文件的增量修改；尚未完成三个模块全部功能，也未发布到服务器。

- 知识资料：上传只形成内部草稿；详情与编辑受租户、科室和管理权限控制；校订产生新版本；支持来源、院区、用途、有效期和院方线下确认凭据；候选准备检查前置条件，仍保持未对客发布。历史自动索引记录同样不能进入公开检索。页面上传、校订 v2、确认、候选流程已实测。

2026-09-09 的 M1 增量补齐了三处前台可用能力：预算、联系时间、沟通风格和医生偏好记录消息 ID、摘要指纹、轮次及提取方式；项目切换时失效不再适用的医生偏好。人工接管快照新增当前目标、项目、医生、待补字段及字段来源，收件箱直接展示接管所需摘要。资料库列表新增服务端关键词、状态、内容类型和公开范围组合筛选，版本详情显示相邻版本的业务字段变更摘要。

**本次没有把“候选准备”当作“发布完成”。** 新资料的正式构建、评测、激活及回滚尚未与旧发布系统接通。当前管理员/售前两角色模型、知识草稿本地 JSON 存储、原渠道人工发送、工时计时及重叠处理仍需下一批开发。

## 优先级与推进顺序

P0：先解决错误回答、上下文错用、人工接管失效、草稿越过发布边界等已复现问题，并维持现有安全门禁。表中 P0 表示功能组重要性，不表示该组所有场景已经完成。

P1：补齐业务闭环和正式交付必需能力，包括五类岗位分权、原渠道人工收发、正式发布流程、可追溯计时与结论。P1 同样是相应功能正式上线的前置条件。

P2：在闭环稳定后完善灰度及使用效率。被列为 P2 的 PRD 一期项仍保留在交付范围，不能据此省略验收。

建议依赖顺序：**身份和持久化 → 实体及资料维护 → 正式知识发布 → 原渠道接待与送达控制 → 工时与质检 → 灰度和完整验收**。身份、知识模型和渠道接口可以由团队按可用人力分工推进；本计划未假定已经配置这些人员。

## 下一迭代先做的六项

1. 建立五类后台角色的服务端能力矩阵：售前顾问/前台、内容专员、发布与索引管理员、质量与运营人员、系统管理员。管理员不自动继承发布或敏感导出权限。终端客户单独作为公共身份。
2. 为知识资料、版本、院方确认、公开许可和候选准备建立 PostgreSQL 事务模型与不可变历史，替换当前单进程 JSON 写入假设；保留当前版本冲突和幂等语义。
3. 统一规范项目、术式、方式及医生项目关系 ID；将已落地的预算、时间、风格、医生来源机制扩展到全部业务字段，并补置信度、确认状态、话题版本及管理端原消息定位；用未参与调试的多轮集核验泛化效果。
4. 在已完成的组合筛选和字段级版本摘要上，补资料独立详情、媒体校订、逐行差异和受控恢复；根据 D06 确认后落实限额及扫描件回补。
5. 冻结候选包、评测结果、原子激活和撤销接口，迁移旧三审依赖；未完成迁移前保持新资料不对客发布。
6. 冻结人工消息、归属版本、outbox 和回执协议；先跑网页通道，再接入具备官方授权的企业微信和抖音。人工接管、取消、转交均在真实发送前复核。

## 跨模块依赖与边界

- **院方输入**：D01 资料联系人及可接受的线下凭据，D02 有效服务政策，D05 接待工作时段/提醒/升级规则，D06 文件格式与限额需业务确认。未取得的凭据不虚构、不默认批准。
- **正式发布**：新候选需要有内容、媒体和关系版本、有效公开许可、文本及图索引、策略与评测绑定。当前只登记候选状态，不提供已完成构建或已发布的虚假记录。
- **多实例可靠性**：本批知识维护依赖本地 JSON 的同步写入；不能作为多进程事务保证。接管修复位于领域服务与 HTTP 返回边界，尚不等于真实 IM 发送器和 PostgreSQL/outbox 的完整原子保证。
- **工时**：当前仍是手工分钟记录，不得将其包装成开始/暂停计时或准确的人效节省结果。M3 处理同顾问重叠区间及核实。
- **关联模块**：产品目录、医生目录、公开媒体许可、真实身份和渠道接入是上述闭环的依赖。预约登记仍有“排班前置”的 V1.2 差异；本批没有修改预约逻辑，应进入后续关联改造，不把它当作已完成。
- **环境**：本地规则/模拟模型验证不代表真实模型质量验收；本次没有执行真实 IM 发送、正式 GraphRAG 重建、生产发布或新增 PostgreSQL 集成验收。

先运行本批回归和既有安全/身份/发布测试，再用独立测试数据覆盖 PRD 场景。每个场景保留输入、原消息ID、状态、回复或静默结果、证据版本及服务端日志。不能因全部脚本通过而宣布一期功能全部完成。
