# 售前智能体独立服务架构（v1.1）

## 1. 本轮调整结果

售前智能体继续作为独立业务服务运行，不从属于网页页面或某一个渠道。本轮在原有“渠道适配 + 问答核心”的基础上增加了四项底座：

1. **租户隔离**：会话、客户身份、运行审计、转人工任务、知识发布都带 `tenant_id`。
2. **持久化边界**：会话、转人工、运营任务和知识发布状态不再只依赖进程内存。
3. **人工接管闭环**：风险触发会创建任务和 SLA；坐席接管后暂停 AI，完成人工处理后恢复。
4. **知识发布准入**：正式环境只允许业务、医务、合规三审后发布的记录进入对客检索。

```text
网页 / 企业微信 / 合作方渠道
            │
            ▼
     渠道连接器与身份映射
            │  统一消息协议 v1.1
            ▼
┌──────────────────────────────────────┐
│          售前智能体服务 4180          │
│  意图与会话 ─ 知识检索 ─ 回答策略     │
│       │            │                 │
│  转人工任务中心   知识发布门禁          │
│       │            │                 │
│  人工工时计量     版本/三审/审计         │
└──────────────────────────────────────┘
            │
      网页与管理网关 4173
```

网页、企微和通用 API 共享相同的意图、知识、会话、回答与安全规则。新渠道只增加入站和出站适配器，不复制智能体。

## 2. 服务与数据边界

| 单元 | 默认地址 | 当前职责 |
|---|---|---|
| 网页与管理网关 | `http://127.0.0.1:4173` | 页面、公开网页问答、留资、管理 API |
| 售前智能体 | `http://127.0.0.1:4180` | 渠道消息、问答核心、会话、转人工、知识准入、运行状态 |
| 知识包 | 只读目录 | 原始知识记录与证据 |
| 状态存储 | 本地 JSON 适配器 | 单实例试运行的会话、任务、工时与发布状态 |

当前本地 JSON 是持久化接口的首个适配器，解决“重启即丢失”和领域代码直接依赖内存的问题。它**不支持多副本并发写入**。进入真实试点前，应把相同接口替换为 PostgreSQL（业务事实与审计）和 Redis（短期会话、幂等、锁与限流）；领域服务和渠道协议无需随之重写。

## 3. 统一消息协议 v1.1

会话隔离键为：

```text
tenant_id + channel + conversation_id
```

请求示例：

```json
{
  "schema_version": "1.1",
  "tenant_id": "huamei-shanghai",
  "channel": "api",
  "conversation_id": "partner-conversation-001",
  "message": {
    "id": "partner-message-001",
    "text": "想做胸部整形，推荐哪个医生？",
    "timestamp": "2026-08-25T10:00:00+08:00"
  },
  "actor": {
    "external_user_id": "external-customer-001",
    "customer_id": "C-001"
  },
  "context": { "owner": "在线咨询组" },
  "interests": ["胸部整形"]
}
```

网页网关在部署时固定绑定 `HUAMEI_PUBLIC_TENANT_ID`，公网请求不能覆盖租户。其他渠道由 `HUAMEI_ACQUISITION_CLIENTS_JSON` 将 `caller_id` 绑定到允许的 `tenant_ids` 和最小权限；请求 payload、query 和 header 中的 `tenant_id` 只做一致性校验，不作为授权依据。返回结果增加 `tenant_id` 和 `delivery`：当人工已接管时，`delivery.suppress_ai=true`，渠道连接器不得再发送 AI 文本。

## 4. 转人工执行闭环

风险门禁或客户主动要求人工时，系统执行以下状态流转：

```text
handover_required
      │ 创建 handover + task + SLA
      ▼
   pending ──坐席接管──> active（暂停 AI）
                              │
                         人工处理完成
                              ▼
                         completed（恢复 AI）
```

主要接口：

- `GET /v1/handovers`：按租户查询接管任务。
- `POST /v1/handovers/{id}/claim`：坐席接管，AI 进入静默。
- `POST /v1/handovers/{id}/complete`：完成人工处理，恢复 AI。
- `GET /v1/operations/tasks`：查询运营任务。
- `POST /v1/operations/human-work`：登记售前人员实际付出分钟数。
- `GET /v1/operations/metrics`：查询接管 SLA 和人工工时汇总。

人工工时接口是立项指标“相同服务水平下减少售前人员付出时间”的计量底座，但单有系统日志不能直接证明下降 30%；仍需建立同口径基线、客户服务量分母、连续四周数据和质量护栏。

## 5. 知识发布准入

知识源目录只读挂载，发布状态与源文件分开保存。正式环境配置：

```bash
HUAMEI_KNOWLEDGE_APPROVAL_MODE=enforce
```

`enforce` 模式下，没有有效发布版本，或记录不在 `approved_record_ids` 中，就不能进入对客检索。发布必须同时提供：

- 业务审核人及 `approved` 结论；
- 医务审核人及 `approved` 结论；
- 合规审核人及 `approved` 结论；
- 知识包版本、允许对客的记录 ID、有效时间。

本地开发默认 `preview`，便于使用现有待审资料验证问答逻辑。健康状态会明确返回预览警告；预览模式不满足正式试点准入。

相关接口：

- `GET /v1/knowledge/admission`
- `GET /v1/knowledge/releases`
- `POST /v1/knowledge/releases`

## 6. 企业微信边界

当前服务接受连接器解包后的 JSON，并兼容 `MsgId`、`FromUserName`、`Content`、`CreateTime`、`ToUserName` 等字段。生产连接器仍需负责：

1. 回调 URL 校验、签名校验与 AES 解密；
2. 企业与外部联系人到 `tenant_id`、`external_user_id` 的映射；
3. Token 生命周期、消息发送、送达回执、重试和失败队列；
4. 收到 `delivery.suppress_ai=true` 时停止 AI 发送，把消息交给坐席；
5. 接管完成后调用完成接口恢复 AI。

企微凭据不进入售前智能体服务，避免渠道密钥、协议升级和问答业务耦合。

## 7. 部署和安全

生产环境必须配置调用方注册表。每个网页网关、企微连接器或管理后端使用独立的 32 位以上随机 secret，配置允许租户和权限（如 `conversation:write`、`operations:read`、`knowledge:release`）。调用方必须同时提供 `X-Caller-Id` 和 `X-Service-Key`；两者不属于同一注册记录时统一拒绝。4180 仅应位于私有网络。

当前已经具备的安全基础包括：服务间密钥、限流、幂等、手机号与证件号脱敏、租户作用域、只读知识挂载和对客知识准入。正式试点仍需继续补齐：统一身份与 RBAC、租户级密钥、不可篡改审计、PostgreSQL/Redis/消息队列、监控告警、备份恢复和医院安全评审。

## 8. 下一阶段架构任务

1. 把本地状态适配器替换为 PostgreSQL + Redis，并增加 Outbox 事件投递。
2. 建设真实企微连接器和消息失败重试队列。
3. 将模型调用抽成独立模型网关，支持供应商切换、BYOK、出域策略和成本计量。
4. 将转人工、知识发布和 Bad Case 接入真实运营后台。
5. 接入预约/排班与 CRM，形成创建、回执、改期、取消闭环。
6. 建立四周业务试验看板，计算每服务客户人工分钟数、净节省工时与服务质量护栏。
