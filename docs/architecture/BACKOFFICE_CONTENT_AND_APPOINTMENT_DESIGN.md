# 华美一期后台：内容维护、科室权限与预约通知设计

版本：1.1  
状态：一期内部闭环已实现（本地单实例交付）  
适用范围：PC 管理后台、售前智能体服务、内部知识录入、内部预约/排班

## 1. 目标与边界

本设计补齐售前智能体的后台运营闭环：医院人员可以低门槛录入和更新知识；每一条知识只能由有范围权限的人员维护；客户提出预约后，前台可以在本系统内确认排班与接待。本期不连接任何外部业务系统。

三项底线：

1. 上传资料先进入**待审核区**，不直接进入对客知识库，也不直接被智能体引用。
2. 科室主管只可维护自身科室及其项目范围；不能修改其他科室、医院级经营资料、角色权限或已激活的对客版本。
3. 客户的“想预约”是**预约意向**，不是已预约成功；只有前台核验排班并明确确认后，才可写为预约确认。

## 2. 信息架构

在现有“知识与合规”模块增加两个工作区；“人工接管”工作台增加一个预约提醒入口。

| 位置 | 工作区 | 主要使用人 | 目的 |
| --- | --- | --- | --- |
| 知识与合规 | 内容录入 | 科室主管、内容专员 | 上传、解析、打标、修订本部门资料 |
| 知识与合规 | 准入与发布 | 发布经理、业务/医务/合规审核人、索引管理员 | 查看候选范围、三审、图谱绑定与对客版本 |
| 人工接管 | 预约提醒 | 前台、预约专员、值班主管 | 接收预约意向、核验排班、确认接待安排 |

## 3. 自主知识维护流程

### 3.1 录入入口

PC 端“内容录入”支持选择 TXT、Markdown、CSV、JSON 文本资料，并在浏览器读取后由服务端完成受控文本解析。DOCX、PDF、图片型 PDF、扫描件、视频及语音不被伪装成“已解析”；它们将在后续 OCR/转写隔离队列完成后才允许提交审核。

上传表单必填字段：

- 所属科室；
- 内容类型（项目介绍、医生介绍、服务流程、活动/权益、素材海报、排班说明）；
- 项目/医生标签；
- 对客范围（候选对客、仅内部）；
- 生效时间、失效时间和内容负责人。

系统自动生成：文件指纹、原文提取结果、标题建议、实体/标签建议、重复内容提示、敏感表述与时效风险提示。AI 只做建议，不能替代分类、审核或发布决定。

### 3.2 状态机

`已上传 → 解析中 → 待补充 → 待科室确认 → 待医务审核 → 待合规审核 → 对客候选 → 已纳入发布包 / 仅内部归档 / 已退回 / 已下架`

- 任意资料内容、标签、有效期或所属科室变更，均产生新版本并重新进入对应审核。
- 对客候选只能进入新的发布草稿，仍需独立业务、医务、合规三审与正式图谱绑定。
- 活动、价格、排班和医生出诊类内容必须附生效时间与权威源；到期自动停止对客检索。

### 3.3 上传与解析安全要求

- 文件大小、扩展名、MIME、压缩包层级与解压后大小均受限；拒绝可执行文件、密码包、符号链接和宏脚本。
- 当前文本资料以内部草稿记录保存，完整原文不在管理端列表或客户接口返回；生产扩展时原始文件应进入加密对象存储隔离区，由隔离解析任务先做病毒扫描。
- 原文、提取文本、版本差异、审核意见和操作主体均形成审计记录；浏览器不缓存原始资料。
- 解析失败只展示失败原因和重新上传入口，不把不完整原文写入对客知识库。

## 4. 角色、科室和数据范围

生产身份由企业 SSO 的实名主体、角色、`tenant_ids` 及 `department_ids` 范围决定，前端不得通过下拉框模拟或扩大权限。本地交付环境只允许回环管理身份，用于完成单机验收；上线前必须切换为受验证的 OIDC 身份。

| 角色 | 典型范围 | 可执行操作 | 不可执行操作 |
| --- | --- | --- | --- |
| 平台管理员 | 全院 | 配置科室、角色、连接器与审计查看 | 代替医务/合规做审核或激活版本 |
| 科室主管 | 本科室及项目 | 上传、编辑、提交科室确认、查看本部门资料 | 修改其他科室、跨院资料、对客发布 |
| 内容专员 | 授权科室 | 上传、标注、修订草稿 | 提交科室确认、发布 |
| 业务审核人 | 授权院区 | 业务审核 | 医务、合规审核 |
| 医务审核人 | 医务范围 | 医疗表述审核 | 业务、合规审核 |
| 合规审核人 | 全院合规范围 | 合规审核、下架建议 | 医务审核、激活发布 |
| 索引管理员 | 全院 | 绑定正式 GraphRAG 索引 | 修改原文、激活版本 |
| 发布人 | 全院 | 激活已完成三审与索引绑定的版本 | 编辑审核结论 |
| 前台/预约专员 | 本院区或门店 | 查看并处理预约提醒、确认接待 | 查看未授权科室原始知识、修改对客知识 |

权限判断必须同时满足：角色许可、租户许可、院区许可、科室许可和资源归属；写操作要带稳定幂等键与审计事件。

## 5. 预约提醒与前台确认

### 5.1 触发规则

智能体识别到明确预约诉求，并收集到“意向项目或医生”以及“时间偏好”后，且客户已经完成本次服务联系方式验证，才创建一条 `预约待确认` 事项。若信息不足，智能体只继续补问必要字段，不生成伪预约。

提醒卡片只展示完成接待所需的最小信息：渠道、会话号、意向项目、意向医生、到院日期/时段、当前已确认字段、创建时间及客户联系方式是否可在本次服务目的下查看。手机号默认脱敏，显式查看需单独权限和审计。

### 5.2 前台处理状态

`待确认 → 已领取 → 核验排班 → 已确认 / 待客户补充 / 无可用时段 / 已取消 / 已过期`

- “已确认”必须由前台在本系统已配置、有效且未满的内部排班时段中确认后，生成可追溯的内部预约编号；智能体不会自行写入成功状态。
- 当前排班、可约时段和名额由本系统维护，是一期内唯一的预约事实来源；后续接入外部排班系统后，必须先完成来源切换和一致性校验，不能双写猜测。
- 管理端以 15 秒轮询获取新事项及状态变化；实时推送属于后续优化项，轮询失败时页面明确提示未同步。
- 已领取事项需保留处理人、处理时间、排班核验来源和客户确认方式；同一会话、同一预约意图使用幂等键去重。

## 6. 服务契约与数据模型

### 6.1 核心资源

| 资源 | 关键字段 |
| --- | --- |
| `knowledge_intake_document` | id、tenant、department、labels、source_type、storage_ref、content_hash、parser_status、risk_flags、owner、effective_at、expires_at、version |
| `knowledge_intake_chunk` | document_id、chunk_id、text_hash、entity_tags、candidate_audience、parse_confidence |
| `knowledge_change_request` | document_version、state、submitted_by、department_confirmation、medical_review、compliance_review、release_binding |
| `appointment_intake` | id、tenant、channel、conversation_id、project、doctor、preferred_date、time_preference、status、schedule_reference、assignee、created_at |
| `department_scope` | subject、tenant、branch、department、role、effective_at、expires_at |

### 6.2 管理端 API（第一版）

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/admin/knowledge/intake/documents` | `knowledge:intake:write` | 录入 TXT/Markdown/CSV/JSON 文本资料并创建内部解析草稿 |
| GET | `/api/admin/knowledge/intake/documents` | `knowledge:intake:read` | 按科室、状态和标签查看本人有权范围 |
| POST | `/api/admin/knowledge/intake/documents/{id}/submit` | `knowledge:intake:submit` | 提交科室确认与审核 |
| GET | `/api/admin/appointment-intakes` | `appointment:read` | 拉取预约待确认事项 |
| POST | `/api/admin/appointment-intakes/{id}/claim` | `appointment:write` | 前台领取事项 |
| POST | `/api/admin/appointment-intakes/{id}/resolve` | `appointment:write` | 记录排班核验与最终状态 |

正式知识发布仍沿用已有的“新草稿 → 三个独立实名审核 → 正式图谱绑定 → 发布人激活”流程，不由自主上传入口直接发布。

## 7. 交付顺序与验收

### P1：知识录入与范围控制（已交付文本资料链路）

1. 已完成 TXT/Markdown/CSV/JSON 的上传、解析、打标、重复指纹提示与科室范围校验；
2. 已完成内部草稿、提交科室确认、稳定幂等键和服务端审计；
3. DOCX/PDF/OCR、隔离对象存储、病毒扫描、版本差异和三审工作流为后续发布前能力；
4. 生产环境需在 SSO 中提供 `department_ids` 声明与后台角色映射。

验收：非授权用户不能读取、上传、编辑或提交其他科室资料；一份资料从上传到对客候选必须保留完整版本和审核轨迹。

### P2：预约提醒与排班协同（已交付内部排班链路）

1. 已从智能体会话动作生成幂等的预约待确认事项，并要求服务联系方式已验证；
2. 已完成管理端轮询、领取、内部排班配置、名额保护、核验、状态回写和内部预约编号生成；
3. 外部预约/排班系统接入不属于本期范围；接入后应以其结果替换内部排班事实来源；
4. 超时升级、短信通知、实时推送和日报指标为后续运营增强项。

验收：预约意向在目标时延内出现在有权限的前台窗口；无排班核验或无预约号时绝不显示“预约成功”；重复消息不产生重复事项。

## 8. 上线前基础依赖

- 当前独立交付不依赖任何外部业务系统；内部知识草稿与内部预约/排班可在本地单进程环境运行。
- 上线前基础设施：企业 SSO（实名、角色、租户、院区和科室范围）、PostgreSQL（版本、审核、预约事项和审计）、Redis（幂等和任务状态）。
- 后续文档能力：加密对象存储、病毒扫描与 DOCX/PDF/OCR 隔离解析服务。
- 后续业务集成：外部预约/排班系统；接入后才可将其作为排班与预约号的权威来源。
